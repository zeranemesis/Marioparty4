Les rapports partagent le build DAA005…D84, le disque est déclaré identique et la tentative 520425ef… est commune. Le TLS et les heartbeats fonctionnent avant le lancement, avec un ping habituel proche de 21–82 ms et quelques pointes autour de 270 ms.

La connexion finit par être fermée vers 17:57:17Z, bien avant le watchdog natif de deux minutes ; la capture affichée correspond à l’attente commencée avant cette fermeture.

Conclusion étayée : le blocage observé est une livraison à sens unique dans le pont local, de TLS vers le jeu du client. L’attribution précise à l’accès concurrent au même UdpClient est une inférence tirée du code : une tâche faisait Receive tandis qu’une autre faisait Send sur la même instance, opération dont le programme ne garantissait pas le comportement. Le pont v5 donne la propriété exclusive de la socket UDP à une seule tâche. Les paquets TLS reçus sont placés dans une file concurrente ; cette tâche les livre au jeu puis lit ses paquets avec un délai maximal de 5 ms.

Une seconde anomalie a été révélée par le test renforcé : toute vieille entrée était interprétée comme demande implicite de retransmission. Les deux jeux pouvaient alors se répondre indéfiniment et créer des dizaines de milliers de rejets. Le protocole v5 marque désormais uniquement les demandes explicites ; une réponse ordinaire n’en déclenche pas une autre.

Validation : compilation native et compagnon réussie. Tests natifs rollback/transport/runtime réussis. La suite du compagnon passe 85 contrôles et deux processus terminent 1 200 ticks via TLS malgré une pause de 12 secondes et la suppression volontaire d’une entrée. Le diagnostic final montre les deux joueurs progressant au-delà du tick 500, les deux entrées disponibles, zéro erreur d’envoi et 12 réparations ciblées au lieu de dizaines de milliers. Aucun test local ne remplace la vérification entre les deux réseaux réels.
